## 1. 先确定要赢什么

**建议定位：把用户在现有网站上的重复劳动，变成可理解、可修改、可复用、可分享的个人微应用。** AI 负责创作、探索和修复，日常稳定操作尽量由微应用直接执行；本地优先，连接用户选择的 Agent 与模型。

首批仍聚焦多业务系统的 QA、运营、产品和进阶个人用户。先验证 3 类高频任务：跨页填表、业务页面增强、表格与信息整理。把“第一次成功”做成普通同事能完成的体验，再扩到泛消费者。

竞争判断：

- 用户脚本管理器有现成供给和使用习惯；BeeHelper 应降低脚本发现、理解、改造和维护成本，逐项补兼容。
- Sider Code 已进入“描述需求 → 改网页 → 保存脚本”的直接竞争范围；单纯自然语言生成页面脚本已不足以形成差异。[Sider 官方说明](https://sider.ai/en/help-center/feature-guides/code)
- 通用浏览器 Agent 擅长临时完成任务；BeeHelper 的机会是把成功经验沉淀成稳定、有版本、能组合的应用，减少每次重新推理的成本。
- AI 应用生成器争夺创作者与分发；BeeHelper 应强调在用户已有网站与当前浏览器会话中使用，形成创建、运行、修复、分享的闭环。
- “一切皆插件”是可持续扩展的架构原则。用户最终应感知“我能得到什么、现在什么在运行、出问题如何恢复”。

### 值得积累的竞争资产

1. **真实任务的可靠性**：同一应用可重复成功，网站变化后能定位、修复并回归。
2. **可迁移的应用资产**：源码、版本、配置、适配声明、测试样例和来源，用户可导出并保有控制权。
3. **高质量生态供给**：应用通过分享带来使用者，使用者再微调、派生和贡献修复。
4. **跨生态的可信适配**：能力协商、明确支持等级与复现测试，而不是仅增加客户端名称。

## 3. 八个方向的产品与技术落点

### 3.1 零命令安装：把首次运行也纳入安装体验

目标是普通用户从下载到第一次使用无需终端、Node、npm 或源码工程。分成两条路径：

- **仅运行已安装微应用**：优先让扩展自身完成，不强制要求 AI 在线或安装本地 Agent。
- **AI 创作/修复**：引导检测已有 Agent；没有 Agent 时提供可选图形化安装/连接流程，或经验证的内置模型通路。连接器打包并不会自动解决 Agent 本身的安装与登录。

三平台安装包要覆盖连接器、所需运行时、稳定安装路径、浏览器注册、修复与卸载。macOS 验证 arm64/x64 和签名公证；Windows 验证 x64、HKCU 注册、升级中文/空格路径；Linux 先明确发行版与包格式，分别说明用户级安装和系统包管理器权限。

浏览器扩展安装、用户脚本开关、站点授权仍须通过浏览器允许的交互完成。普通用户“零命令”可以实现；“任意电脑双击后无授权即可全自动可用”不能作为统一承诺。[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)、[userScripts](https://developer.chrome.com/docs/extensions/reference/api/userScripts)

### 3.2 更新：一个入口，三条通路

| 更新对象 | 推荐通路 | 用户体验与约束 |
| --- | --- | --- |
| 扩展包与随包内置插件 | Chrome Web Store / 各浏览器商店正式更新 | 更新中心展示状态、发行说明和待应用原因；浏览器控制分发节奏，不能承诺即时推送 |
| 本地连接器与运行时 | 原生安装器/更新服务，签名清单、原子替换、健康检查 | 扩展通过受限协议请求检查与安装；活动任务结束后切换，失败回退；不让扩展直接写本地二进制 |
| 用户微应用 | 发布清单 + 固定版本快照 + 可选订阅 | 未本地修改且无新增权限时按用户策略更新；本地派生与上游更新冲突时保留两者，扩权时重新确认 |

自动更新默认尽量无操作，但要有暂停、固定版本、稳定/预览通道、离线重试及结果可追溯。先按扩展启动和连接器启动检查；需要“浏览器未打开也更新”时，再评估 OS 调度机制与用户偏好。不要为接收版本通知先建立长期在线推送连接。

运行中的会话、源码写入和页面实例不能被强制重载打断。更新前做数据迁移与恢复演练；连接器可做 A/B 回退，扩展回退受商店机制约束，不能统一承诺任意版本降级。Chrome 通常自动检查更新，避免频繁轮询 `requestUpdateCheck()`。[Runtime 官方文档](https://developer.chrome.com/docs/extensions/reference/api/runtime)

### 3.3 语言：明确“主机语言”与“浏览器语言”

提供“自动 / 指定语言”。自动模式优先使用已连接原生宿主明确返回的 OS 界面语言；宿主不可用时退回浏览器 UI 语言，再退回支持的基础语言及英文。界面说明当前采用的语言来源，避免把浏览器语言误称为 OS 语言。

先交付简中与英文及完整资源化，再依用户分布增加繁中、日语、西语等语言。安装器、扩展商店描述、权限与错误提示、日期数字、教程均纳入。AI 回复语言与应用 UI 语言可独立设置；第三方源码与用户内容不被自动改写。[Chrome i18n](https://developer.chrome.com/docs/extensions/reference/api/i18n)

### 3.4 当前页面与文件夹：用真实运行实例表达生效状态

“已安装”“已启用”“匹配当前页面”“当前运行/持续生效”“被权限或错误阻止”是不同维度。以目标 `tab/document`、应用与 revision、运行实例为依据，展示状态及原因，不能用 URL 命中或旧日志推断“正在生效”。

侧边栏顶部增加当前页面摘要，工具栏角标显示实际生效数量，详情支持跳转目标页、查看版本与日志、停止/禁用。多标签页并行、SPA 导航、页面刷新和后台恢复都要避免显示过期状态。

文件夹先做移动、重命名、排序、批量操作，再增加标签与智能视图。组织关系与启用规则分开；把应用移进文件夹不能暗中改变权限或自动运行范围。批量关闭要能看到影响哪些页面。

### 3.5 社区：先让分享成立，再扩社交功能

把“本地可用”“云同步”“公开分享”作为独立用户选择。Google/GitHub 优先提供身份登录，微信按目标地区和开放平台申请条件接入，支持多身份绑定与找回；登录账号不等于授权访问用户仓库、云盘或业务页面。

分享链接指向说明、作者、版本、适用站点、能力需求与源码预览。接收者无需登录即可查看，安装时取得确切快照，进入候选或按显式选择安装。公开链接不嵌入 cookie、token、业务数据或用户私有配置；有明确撤回、删除与举报机制。

同步首先覆盖用户主动选择的应用定义与组织偏好；聊天、附件、私有存储、业务页面内容和凭据不默认上传。私有数据的加密、密钥恢复与冲突规则须在开放同步前落地。小范围分发先用不公开收录链接；不公开收录不等于访问控制，团队私密分享后续增加真正的成员鉴权。

### 3.6 兼容：建立多维能力矩阵

| 层次 | 建议顺序 | 验收边界 |
| --- | --- | --- |
| OS/架构 | macOS arm64/x64、Windows x64、指定 Linux 发行版 | 安装、发现 Agent、连接、运行、升级、卸载均测；Windows arm64另列 |
| 浏览器 | Chrome 稳定版 → Edge → 需求驱动的 Brave/Firefox → Safari 可行性 | 侧边栏、userScripts、Native Messaging、扩展来源 ID 分别适配；同为 Chromium 也须实测 |
| Agent 客户端 | 现有 Codex/Claude/dsh 做稳定性 → 按用户需求新增 ACP 客户端 | 协议版本、会话恢复、取消、授权、附件、模型目录、命令能力逐项声明；桌面安装不等于 API 可控制 |
| LLM | 先通过已有 Agent 协商；再验证可选内置 provider 路线 | 不只看接口路径；实测工具调用、流式事件、视觉、上下文、认证、配额与错误 |
| 网络 | 直连、用户已有代理、企业代理/PAC、断网、受限来源 | 分清扩展网络与本地进程网络；支持自定义端点与授权镜像，不传送凭据给不明中继 |
| 页面与脚本 | SPA、开放 Shadow DOM、常用 GM API、可访问 iframe | 为每个不支持项提供原因和替代；闭合 Shadow DOM、受限页与跨源 iframe 不虚报支持 |

支持等级统一为“已验证 / 实验 / 不支持”，附版本、平台与核验日期。重试按操作语义设计：可安全重试的发现/下载和有副作用的提交不能共用自动重试策略。

加速优先做来源缓存、资源按内容哈希复用、增量下载、应用直接运行与按需发送上下文；再比较延迟/成本。模型故障切换必须遵守用户的数据去向和费用设置，不静默转给另一供应商。

### 3.7 门户与教程：让每个示例变成成功路径

门户展示能解决的任务、三平台入口、兼容矩阵和 13 个 Demo。人类教程按“我要完成什么”组织，包含预期效果、适用页面、操作步骤、常见失败与恢复；快速入门优先使用无需真实业务账号的测试页。

AI 文档提供带版本的 Markdown、SDK 类型/Schema、能力清单、最小示例与可复现错误；从真实接口或构建产物生成关键参考页，文档示例运行回归。`llms.txt` 可作为索引入口，但不能替代准确内容、版本和普通可抓取页面。

### 3.8 一切皆插件：统一能力契约，保留最小可信底座

建议分为三层：

1. **最小底座**：启动、身份与消息校验、能力授权、存储迁移、包校验、插件装载和故障恢复。它必须能在管理 UI 或更新 UI 损坏时工作。
2. **内置系统微应用**：AI 会话、微应用管理、版本更新、教程与诊断，使用共同的 manifest、导航注册、状态与生命周期；核心项标记不可卸载。需要特权的实现随扩展静态打包，界面通过受限服务接口调用。
3. **用户/社区微应用**：在 userScripts 或 sandbox 等适当环境执行，通过授权 SDK 访问宿主；能组合和替换可开放的界面能力，不继承系统特权。

不要把“都叫微应用”实现成任意远程代码能在扩展特权页执行。版本更新界面可以是内置微应用，但二进制校验、原子替换和恢复仍归可信服务。内置系统微应用的代码更新走宿主发布通路，第三方分享通路不能覆盖它们。[MV3 远程代码说明](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)

插件清单建议包含标识、版本、入口、内置/可卸载属性、能力依赖、宿主兼容范围、迁移与清理契约。先迁移一个非关键内置界面作为纵向验证，再改会话和管理入口；不为插件化暂停全部产品交付。

## 5. 发布门槛、指标与资本叙事

### 先用数据决定是否扩张

以下是小规模试点的起始假设，S01 后重新标定，所有指标同时记录样本数与观察窗口：

| 指标 | 定义 | 建议起始目标 |
| --- | --- | --- |
| 安装完成率 | 开始安装且完成首次可用检查的人数 / 开始安装人数，按 OS 分组 | ≥90%，每个承诺平台至少 5 台独立环境；样本小只判断主要阻塞 |
| 首次价值时间 | 开始安装到完成第一个目标任务，分别记录纯运行与 AI 创作 | 中位数 ≤5 分钟，P90 ≤15 分钟；外部 Agent 登录时间单列 |
| 7 日复用 | 激活用户中 7 日内在不同日期再次成功运行自己应用的比例 | 先争取 ≥40%，同时展示小样本区间与失败原因 |
| 任务成功率 | 用户认可结果且有运行证据的成功次数 / 明确尝试次数，按任务/版本分组 | 3 类核心任务 ≥95%，同时记录未知/取消；不从“无异常”推导业务成功 |
| 分享激活率 | 打开分享链接的新用户中安装并成功运行的人数 / 有效新访客 | 建基线后再设阈值；区分查看、安装、首跑和再次复用 |
| 维护成本 | 每个周活应用的故障率、人工修复时间、平均模型调用成本 | 对比旧版或纯 Agent 路径持续降低，不预设虚构节约比例 |

安装数据采用用户同意的最小事件或人工观察；运行日志与业务正文不默认变成遥测。团队付费前同时记录每活跃用户的存储、下载、模型、支持成本。

### 阶段出口

- **进入扩大分发前**：S02–S07 和 S12 的目标平台闭环成立，能发现错误、升级和恢复；S09/S11 支撑目标语言用户使用。
- **扩大开放社区前**：M01/M05 的版本与本地修改保护成立，来源、删除和滥用响应可用，先证明分享带来复用。
- **扩大商业投入前**：有连续数周复用、可解释获客来源、真实付费与单位成本证据；企业/无人值守路线另立试点。

### 资本兴趣如何变成 TODO

调研中的浏览器 Agent、AI 应用生成器及插件生态融资，说明这些问题获得投资者关注；融资额和估值不证明 BeeHelper 有同样市场，也不能替代使用数据。具体官方公告、日期与口径见[调研报告](research/2026-10-24-competitive-ecosystem-research.md)。

建议长期叙事是：**AI 产生应用，应用沉淀可复用能力，复用降低推理与维护成本，分发带来更多使用者和维护者。** 对应必须验证的事实分别是 S14/M07 的可靠性、M01/M05 的传播与演进、M06/L02 的生态、M16 的商业可持续性。投资者可能关心留存、供给质量、分发效率与单位经济性，这是建议的观察框架，不是已证实的投资意向。

## 6. 暂缓项与主要决策点

- 不以同时兼容全部 OS/浏览器/Agent/模型作为首发条件；公布目标和支持等级，逐批兑现。
- 不先做通用桌面外壳、自研完整 harness 或大型插件市场；先验证已有浏览器任务的留存。
- 不把第三方订阅额度、桌面登录态或用户 cookie 当作可任意复用的公共资源。
- 不把“自动修复”变成生产页面上无限重试；源码恢复、实例清理与外部业务撤销分别说明。
- 不因社区化强制所有用户注册，不因统一更新界面混淆三种更新权限。
- 近期需通过实验决定：无 CLI 用户是否需要内置模型通路、Linux 首发发行版、分享包的站点权限粒度、私有同步范围与加密恢复、商店对具体微应用执行/分发方案的审查结果。

上述限制服务于本轮目标的可实现性，不改变“尽量插件化、降低使用和分发成本”的方向。
