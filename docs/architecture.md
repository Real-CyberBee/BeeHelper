# BeeHelper 技术方案初稿

日期：2026-10-18。状态：设计基线；已开始本地验证版实现。

当前实现选择 Chromium MV3、React/TypeScript/Vite、Cordis core、扩展本地存储、userScripts/sandbox，以及 Native Messaging + Codex App Server + MCP。用户日常入口为原生侧边栏，不以完整标签页替代。[本机测试](local-testing.md)与[项目说明](../README.md)记录当前操作方式；下面保留最初设计与待验证项，不能将其全部视为已完成。

[产品需求](product.md)记录已确认方向；本文中的运行时、接口名称、存储与部署方式均为工程建议，不能视为已有兼容性或端到端验证结果。

## 1. 设计目标

- 用户在侧边栏完成对话、微应用管理、源码修改、运行和观察。
- 候选无需先安装即可看效果，随后一键保存到本地库。
- 微应用源码以 BeeHelper 管理的数据为准，不要求用户维护磁盘工程。
- 复用外部 Codex 的 agent 循环，不在首版重写 harness。
- everything-is-a-plugin 用于组织可替换能力，不等同于任意代码能在任意扩展上下文动态加载。
- 首版不增设企业审批或业务规则；通信鉴别、版本一致性和资源清理是技术正确性要求。

## 2. 建议的运行结构

```text
BeeHelper 侧边栏 / 页面入口
        |
浏览器扩展：插件组合、候选与安装库、源码版本、运行与观测
        |                              |
页面脚本 / 隔离界面运行环境      本地 Codex 连接器
                                       |
                                Codex App Server
                                       |
                           BeeHelper 工具调用与结果回传
```

浏览器目标建议先验证 Chromium MV3；具体浏览器、最低版本与系统支持范围尚未确定。

本地连接器是建议交付方式：用户只需一次安装/连接，不需要手动启动多个终端或管理微应用工程。连接器只管理通信和已有 Codex 运行时，不实现另一套 agent loop。

## 3. 插件组合

仅保留浏览器要求的 manifest 与启动入口。库、存储、运行环境、Codex 连接、工具注册、编辑与结果呈现等能力按 Module 组织，通过小型 Interface 组合。

Cordis core 是插件生命周期候选；依赖版本、上游或 dsh fork 的选择仍需验证。已有轻量 smoke 仅覆盖 core，不覆盖完整 loader 或扩展运行。[R1]

必须区分两种分发和执行方式：

| 类型 | 首版建议 | 不能混同 |
| --- | --- | --- |
| 扩展能力插件 | 可信实现随扩展静态打包，使用服务注入、事件和卸载清理 | 可替换不等于可绕过 MV3 动态代码限制 |
| 用户微应用 | 作为源码与资源保存，交由适当运行环境执行 | 安装微应用不等于把源码求值到特权扩展页面 |

先实现实际需要的插件，不预建通用插件市场、任意 npm 安装器或多 agent 框架。

## 4. 源码、候选与安装库

建议由一个浏览器侧 storage Module 持有权威数据。IndexedDB 是源码、资源、版本和运行记录的候选；小型偏好设置可以独立存储。连接器不拥有第二份可自行修改的权威源码。

建议的数据关系：

| 对象 | 关键职责 |
| --- | --- |
| Candidate | 未安装源码、资源、说明与当前 revision；可编辑、试用、丢弃 |
| InstalledApp | 已安装项的身份、当前 revision、收藏、配置和启用状态 |
| Revision | 不可变源码/资源快照、父版本、来源与时间 |
| TrialSession | 临时运行、目标页面、revision、已登记的监听和资源 |
| RunRecord | 运行身份、触发来源、确切 revision、状态、观测与错误 |
| ConversationBinding | BeeHelper 对话与 Codex thread/turn 的关联，不内嵌登录凭据 |

持久化的未安装草稿不等于已安装；是否保留用于恢复可以由存储策略决定，不能自动加入库或永久注册页面触发。

### 直接看效果与一键安装

- `查看效果`：以选定 revision 创建 TrialSession；不以 InstalledApp 存在为前提。
- `安装/保存`：把选定 revision 与资源原子加入本地库；可从候选直接调用，不要求先试用。
- `继续修改`：产生新 revision；当前试用运行仍对应原快照，重载时才切换。
- `结束试用`：清理登记的监听、页面增强和通道，不保留长期自动触发。
- `试用后安装`：安装同一 revision，不重新生成代码；处理好试用与正式实例的交接，防止重复监听。

以上为 Interface 行为草案，不是已冻结的方法名。安装按钮是直接入口，不通过导出再导入，不额外插入强制发布审批。

## 5. 动态执行与能力接口

首版应验证以下路径，而不是在普通扩展页执行任意源码：

| 需求 | 候选运行方式 | 验证重点 |
| --- | --- | --- |
| 页面脚本、事件监听、页面增强 | userScripts 与受控的能力通信 | 用户启用条件、页面匹配、单次试用与已安装触发、SPA 重入及清理 |
| 微应用自有交互界面 | 扩展 sandbox 页面 | 动态代码、资源加载、渲染、与宿主通信 |
| 扩展权限动作 | 随包静态能力插件 | 站点权限、调用来源与目标校验、结果回传 |
| WASM 或较重计算 | 扩展文档/offscreen + Dedicated Worker | CSP、生命周期、工具链；不把 PWA 当作前提 |

这些路径的官方限制见 [R2]。userScripts 与 sandbox 的最终组合、源码格式、依赖处理方式都必须经过验证，不能只凭能力列表宣布可用。

微应用使用统一能力 Interface 访问页面、输出、存储和宿主能力，隐藏底层消息通道。不把其设计成固定工作流 DSL。

“查看效果”分两种实际行为：隔离界面展示，或在真实页面临时运行。真实页面运行不是统一 dry-run；网络提交和其他业务副作用不会因为结束试用而自动消失。

## 6. 页面生命周期

- 主动运行绑定当时的目标 tab/document，不在标签页切换后悄悄改目标。
- 页面自动激活基于当前启用配置和页面匹配规则；支持 SPA 路由与文档变化。
- 每个激活实例有独立身份；同一页面重复加载不得重复登记同一实例的监听。
- 试用、已安装运行、禁用和卸载共享同一套资源登记/清理机制。
- 插件卸载、页面离开和运行取消清理可控制资源，不承诺撤销外部业务操作。
- 后台被终止后从持久状态恢复管理界面；不能据此盲目继续半次业务动作。

## 7. Codex 控制通路与工具通路

建议使用本地连接器启动或连接一个受支持的 Codex App Server，通过 stdio 驱动 BeeHelper 自己的会话。官方提供会话、turn 和事件接口；不要默认可以接管用户在其他客户端中的任意现有会话。[O1]

控制通路负责发消息、接收流式进度、关联会话和取消；工具通路负责源码和浏览器能力。两条通路必须同时打通，才能形成真实的创作闭环。

首版优先验证 MCP 工具接入。App Server 的客户端动态工具可作为备选，但其接口状态和版本兼容需另行检查，不依赖未经验证的实验性字段。[O1][R3]

建议的工具职责仅包括：

- 查看、创建和修改候选或已安装微应用的源码与资源。
- 观察明确目标页面，并调用浏览器操作能力。
- 对指定 revision 查看效果、运行、重载和读取结果。
- 按用户意图安装/保存微应用、读取版本和运行记录。

Codex 的磁盘 `read/edit` 不直接等同于编辑 BeeHelper 中的源码。应通过上述工具修改权威数据；若 Codex 需要工作目录，由连接器自动管理内部目录，不要求用户维护项目，也不隐式把该目录升级为权威存储。

“生成成功”只有在 BeeHelper 已接收并校验候选后才能成立；“运行成功”和“安装成功”分别由实际执行与持久化结果决定。

## 8. 本地连接器的建议部署方式

首选验证 Native Messaging，把浏览器与本地运行时连接起来，避免要求浏览器直接连接实验性 Codex WebSocket。Native Messaging 需要独立安装/登记 host，不是只装扩展就可用。[R2][O1]

连接器应隔离两种协议：浏览器 Native Messaging 的帧格式与 Codex stdio 的 JSONL 不是同一协议，不能直接透传字节。日志使用独立通道，不能污染协议输出。[C1][O1]

MCP 服务如何交付、采用本地 HTTP 还是其他受支持传输，以及如何按进程/会话注入配置，留待贯通验证；不能默认为所有 Codex 版本都支持同一字段。避免直接覆盖用户全局配置。

安装标识、扩展来源、宿主生命周期、断连恢复与厂商认证属于安装体验的一部分。首版不新增云账户平台，不读取或导出用户已有客户端凭据，也不承诺任意订阅额度复用。[O1][R3]

## 9. 一致性与失败语义

- 源码修改携带基线 revision；发生并发修改时报告冲突，不覆盖用户刚完成的编辑。
- 每次运行锁定源码快照；安装锁定候选快照，避免 AI 持续输出改变用户正要安装的内容。
- 消息关联 conversation、run、revision、目标页面和请求身份，不能仅靠“当前标签页”或全局最新值。
- 自动激活与临时试用必须去重；正式安装接管后，旧试用不能继续产生重复动作。
- 断连后已完成、未完成与结果未知分别呈现；请求去重不等于能保证任意业务动作 exactly-once。
- 重试与失败修复不隐式重新执行已经产生副作用的整条链路；具体业务策略交给微应用。
- 导入是数据处理，不因读取包就执行代码；拒绝损坏包、路径穿越和不支持的格式，不把凭据默认纳入导出。

这些是宿主正确性约束，不是对业务流程新增审批或限制。

## 10. 技术验证顺序

以下为最初的验证计划，当前完成范围以测试与项目说明为准：

| 阶段 | 验证内容 | 通过条件 |
| --- | --- | --- |
| G1 | Codex 与 BeeHelper 双向贯通 | 侧边栏发起任务，Codex 调工具，扩展回传真实结果并继续一轮 |
| G2 | 未安装候选的即时效果 | AI 修改源码后，在明确页面或隔离界面看到同一 revision 的真实效果 |
| G3 | 一键安装与复用 | 未安装候选直接安装，或试用后安装；重启后可检索、收藏和再次运行 |
| G4 | 生命周期与版本 | 自动激活、SPA、停用、试用转安装、源码并发修改不产生重复或错版本 |
| G5 | 导入导出与故障 | 包往返、断连、取消、后台重启和结果未知均有可观察状态 |
| G6 | 首个 QA 样例 | 在获准测试环境核对接口后，验证跨系统任务与多次对话微调 |

G1/G2 若未通过，先修连接和运行模型，不开始堆叠团队平台或更多 agent。验收不预设 QA 表单的生成、提交和重试规则。

## 11. PWA 与后续扩展

不为 WASM 单独引入 PWA。若 sandbox/userScripts 的组合无法满足明确的动态执行需求，再验证独立 Web/PWA Worker 与扩展配合；dsh 的实验性 Worker runtime 是候选，不是已决定依赖。[R1][R2]

其他 agent 可在真实需求出现后增加连接实现；不为首版只有 Codex 的事实预先构建多协议调度平台。团队治理、定时和无人值守、独立登录态继续后置。

## 12. 仍待验证的选型

浏览器与最低版本、首个支持的桌面系统、Cordis 版本、动态代码宿主、微应用格式、前端/构建工具、存储实现、MCP 传输及 Codex 版本范围均未最终确认。

详细验证从 G1/G2 开始推进。初稿编写时尚无实现；目前已进入本地验证版阶段，真实业务样例和未覆盖的运行环境仍不应标记为通过。

## 7. 0.4 增补：视觉、脚本生态与宿主能力

### 视觉与品牌

- 调色板统一为蜜蜂黄浅色：蜜糖金 `#f2ae2b`、奶油底 `#fffdf6`、暖砂边框 `#f0e3c4`、深棕文字 `#3a2a12`，状态色保留低饱和绿/红以区分成功与失败。
- Logo 来自公司网站 `https://cyberbee.top`（`/logo/bee-96.png`、`/logo/bee-512.png`），仓库内放在 `public/logo/`；扩展图标由 512px 图裁切留白后生成到 `public/icons/`，manifest 的 `icons` 与 `action.default_icon` 引用这些文件。
- 新增组件使用 `--bee-*` CSS 变量，历史样式仍保留字面色值，便于后续整体换肤。

### 用户脚本来源适配

```text
脚本市场 UI (ScriptMarket)
      |  userscriptSearch / userscriptImport
      v
background service worker
      |  core/script-sources.ts  ── ScriptCat API / GreasyFork API / 本地文件
      |  core/userscripts.ts     ── 元数据解析 · 匹配规则转换 · GM 兼容层生成
      v
本地库候选（未安装, trigger=manual）──> 工作台 / AI 会话
```

- 网络请求只在后台执行，利用扩展 host 权限绕开网页 CORS；网页预览明确提示不可用。
- 来源与转换分离：新增来源只需要实现“搜索 + 取源码”，转换和兼容层共用一套逻辑，避免两套行为。
- 导入只创建候选，不执行、不安装；默认 `trigger=manual`，自动激活必须由用户显式修改并安装。
- AI 工具 `userscript_search` / `userscript_import` 复用同一实现，能力清单 `shared/capabilities.json` 同时注册，`tests/tools.test.mjs` 校验工具清单与能力清单一致。

### 宿主能力：微应用调用微应用与 AI

`capability()`（后台）在原有 `storage`、`tabs` 之上增加：

| 能力 | 入口 | 语义 |
| --- | --- | --- |
| `appsList` | `bee.apps.list()` | 返回本地库摘要，不返回源码 |
| `appsRun` | `bee.apps.run(id, tabId?)` | 复用 `runApp`，页面脚本必须显式 tabId |
| `appsUpdate` | `bee.apps.update(id, patch)` | 走 `operation` 的 favorite/enable，启用只对已安装项生效 |
| `agentAsk` | `bee.askAI(prompt)` | 复用会话服务的 `chat` 流程，消息附带当前微应用引用与版本 |

- 页面脚本通过 `chrome.runtime.sendMessage` 走 `onUserScriptMessage` 白名单；界面型通过 `panelCapability` 走同一 `capability()`，两条路径语义一致。
- `agentAsk` 要求 native 连接存在，否则返回可操作错误；不伪造排队成功。
- `appsRun` / `appsUpdate` / `agentAsk` 会写入运行日志，便于回溯是谁在什么时候调用了宿主能力。
- 这些能力不绕过既有模型：AI 的修改仍是新 revision，运行仍需用户触发，安装仍需用户确认。

### 示例画廊

- `src/core/demos.ts` 内置 13 个可直接运行的示例（面板与页面脚本），覆盖自我改造、插件组合、页面增强、跨标签页、数据可视化、个性化工具等方向。
- `tests/userscripts.test.ts` 校验每个示例：定义合法、`id` 唯一、说明完整、源码可用 `AsyncFunction` 编译；新增示例无需改测试文件。
- 示例通过普通的 `create` 操作进入候选库，与用户自己创建的微应用没有特殊通道。

## 0.5.0 最小切片落地

首次使用与诊断作为 `beehelper.setup` 内置系统微应用，manifest 声明不可卸载与能力白名单，通用 React 宿主负责懒加载、焦点与错误边界。后台 `system-setup` 服务通过现有 Cordis 宿主注册；页面运行服务新增文档绑定的活动快照，页面脚本不能调用诊断或向导完成服务。系统微应用仍随扩展静态打包，不经过社区动态源码通路。

运行记录增加可选 `documentId`，旧记录自然缺省；真实活动状态还须匹配内存实例、tab、document、URL 和运行状态，旧记录不能单独证明仍在运行。后台重启后的未知状态保留，普通导航清除旧文档实例。

macOS 分发包内置 Node/生产依赖与扩展文件，安装器把完整版本复制到每用户目录，再切换稳定入口并注册 native host；不依赖源码 checkout，预览版扩展仍由用户在浏览器加载。正式签名、商店分发与自动更新另行完成，细节见[首次使用](getting-started.md)。
