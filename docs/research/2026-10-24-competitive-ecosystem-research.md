# BeeHelper 竞品、生态、技术趋势与资本兴趣调研

调研日期：2026-10-24。性质：路线图决策输入，不代表已实现能力或已承诺排期。

仓库基线：`origin/main` 已更新到 `f4bae01`（0.4.0）；现有 13 个 Demo、ScriptCat/GreasyFork 搜索导入与部分 GM API 转换。Tampermonkey 生态属于部分兼容：跨域特权、`@require` 自动加载、部分资源/下载 API、执行时机仍有限制，不能宣传为完整兼容。[当前项目说明](../../README.zh-CN.md)、[用户脚本对接限制](../userscripts.md)

范围：官方产品文档、官方源码与公司/投资方公告。本轮核验网页可访问性与内容，没有实装竞品、测量成功率、购买付费计划或审计公司经营数据。无明确发布日期的页面仅表示检索时可见状态；有历史日期的页面可能被持续编辑。融资为代表性公开案例，不声称穷尽各公司的最新融资。下文分别标记事实、推断和建议。

## 主要判断

1. **“AI 帮你改网页”已经存在直接竞争。** Sider Code 已提供自然语言网页修改、对话迭代和保存脚本后自动应用。因此 BeeHelper 需要突出可维护的微应用资产、复用已有 Agent、运行可观察与跨页面业务流程，不能仅靠侧边栏和生成脚本区分。前半句为官方事实，竞争策略为推断。[Sider Code 帮助](https://sider.ai/help-center/feature-guides/code)
2. **用户脚本的安装、状态、同步和更新已经是成熟基线。** Tampermonkey 的站点脚本状态、运行数量、自动更新、同步和编辑器，以及 Violentmonkey 的跨浏览器同步均有官方说明。BeeHelper 的体验优先级应先覆盖日常可用与可恢复，再扩展平台数量。[Tampermonkey](https://www.tampermonkey.net/)、[Violentmonkey](https://violentmonkey.github.io/)
3. **定位建议：把用户自己的业务经验变成可反复运行、可分享、可修复的浏览器微应用。** 先服务经常操作多个 Web 后台的研发、测试与运营人员，并用实际复用验证是否扩展到非技术用户。这是待验证的定位假设，尚无 BeeHelper 留存、付费或市场规模证据。
4. **“零命令”可以成为目标，“零授权/零安装步骤”不能据此承诺。** 本地 host、Agent 与浏览器扩展有不同分发渠道；Chrome 用户脚本开关仍需用户启用。应区分只运行微应用的用户与需要本地 Agent 创作的用户。[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)、[userScripts](https://developer.chrome.com/docs/extensions/reference/api/userScripts)
5. **资本已经关注浏览器执行基础设施、工作流自动化与软件创作平台；BeeHelper 的机会仍需自己的使用证据。** 融资说明投资者下注，无法证明该产品已达到相同需求强度、经济性或可投资性。代表性公告见资本部分。

## 生态定位：建议验证的切入点

**核心用户假设：** 经常执行跨页面重复流程、能判断结果是否正确、愿意把经验保存并分享给同事的研发、测试与运营人员。先用与仓库既有表单 demo 相近的真实任务验证；从熟人团队获得使用证据，不直接假定消费者市场成立。

**最小价值单元建议：** 微应用 = 可读源码 + 明确权限/适用站点 + 参数与私有数据 + 版本 + 运行结果 + 分享/更新关系。AI 对话是创造和修复工具，长期价值应来自微应用被实际重复使用。该定义是设计建议，不是现有格式描述。

**可能的差异化及验证方式：**

| 假设 | 应收集的证据 | 推翻信号 |
| --- | --- | --- |
| 保留用户已用的 Agent 能显著降低切换成本 | 同一任务下，新用户首次成功时间、连接失败原因、是否反复切回终端 | 安装/连接成本超过复用价值，用户只愿意用托管入口 |
| AI 生成后保存为微应用比反复口头执行更有价值 | 同一微应用的重复成功次数、后续运行耗时/模型消耗、跨用户安装后的成功率 | 绝大多数只运行一次，维护成本高于节省时间 |
| 研发/测试/运营形成可持续的分享循环 | 作者发出链接后接收者安装并成功运行，且产生更新/修复或再次分享 | 只有演示观看，接收者长期无法独立运行 |
| 本地数据与可读源码提升接受度 | 用户因可检查、可导出或本地运行而采用的访谈证据 | 用户更重视托管便捷，不愿承担本地维护 |

建议以“成功完成并可复用的业务任务”为主指标，同时记录首次成功时间、活跃用户复用率、分享转化、失败原因、修复时间与成本。先建立观测基线，再按实际样本定目标；不把下载量、生成数量、GitHub star 或模型调用数当作业务成功。

## 技术趋势与具体影响

### 从猜测页面转向结构化工具

**事实：** WebMCP 2026-02-10 发布早期预览；官方文档于 2026-10-07 更新，说明从 Chrome 149 开始 origin trial，并仍称其为拟议 Web 标准。它通过 JavaScript 与 HTML 表单标注暴露结构化工具。[早期预览公告](https://developer.chrome.com/blog/webmcp-epp)、[当前文档](https://developer.chrome.com/docs/ai/webmcp)

**建议：** 设计“站点明确 API/工具 → DOM 语义定位 → 必要时视觉”的可替换执行策略。中期对一个自有测试站点验证 WebMCP 输入输出、会话状态、失败回退；不要承诺跨浏览器普遍可用，也不要把 WebMCP 与远程 MCP Server 当作同一传输协议。微应用可成为已有页面与 Agent 的桥梁，但需要证明比直接 DOM 控制更可靠。

### Agent、工具与界面协议各有边界

**事实：** ACP 官方仓库定位为连接编辑器与 Agent 的协议；MCP Apps 官方文档支持工具返回可交互 HTML 界面，由宿主在隔离 iframe 中展示，并通过消息调用工具。MCP Apps 于 2026-01-26 宣布正式发布。[ACP 仓库](https://github.com/agentclientprotocol/agent-client-protocol)、[MCP Apps 文档](https://modelcontextprotocol.io/extensions/apps/overview)、[发布公告](https://blog.modelcontextprotocol.io/posts/2026-01-26-mcp-apps/)

**建议：** Agent 接入、浏览器能力和微应用 UI 分成三类适配器，采用能力协商和协议版本范围；先做可验证子集。中长期评估将部分微应用导出为 MCP 工具/UI，拓展分发面；不能据“都兼容 MCP”承诺全部 UI 或任意客户端内部会话迁移。协议对接也不等于拥有模型授权或可复用订阅额度。

### 分发、更新和用户脚本权限决定产品能否交付

**事实：** Chrome Native Messaging 在 Windows 使用注册表，在 macOS/Linux 使用不同目录的 host manifest，且绑定允许的扩展来源。Chrome 138+ 的用户脚本权限仍要求用户开启扩展详情里的开关。MV3 政策限制远程执行逻辑，同时明确列出 userScripts 等特定 API 和隔离上下文的例外；例外不覆盖其余扩展代码或全部用户数据政策。[Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)、[userScripts](https://developer.chrome.com/docs/extensions/reference/api/userScripts)、[MV3 要求，更新于 2024-04-03](https://developer.chrome.com/docs/webstore/program-policies/mv3-requirements)

**建议：** 安装包捆绑受支持 host 运行时、处理浏览器注册和修复；只运行微应用的路径尽量不依赖本地 Agent。更新对象包括扩展、本地 host、内置微应用和用户微应用；内置特权微应用随扩展打包，因此主要使用商店扩展、本地 host、用户微应用三条交付通路，共用兼容矩阵和状态入口。服务端推送是更新发现机制，不是绕过商店更新或远程替换特权代码的授权。

### “一切皆插件”需要稳定内核

这是架构建议：将 AI 会话、管理、教程、诊断、更新界面等做成内置微应用；内核保留身份校验、权限边界、资源生命周期、存储/迁移、插件装载和恢复机制。内置功能不应仅因“不可卸载”而获得对任意网页与系统无限权限。先通过两项核心功能提取 SDK 验证可插拔性，再考虑全面插件化；避免为遵循理念阻塞首次使用。

## 基于证据补充的候选 TODO

以下用于主路线图取舍；阶段按前置依赖划分，不承诺工期。

### 短期：证明首次成功与反复使用

- [ ] **建立竞品实测基线。** 用同一组表单填写、网页定制、SPA 与跨页任务比较 Tampermonkey + AI、Sider Code 和 BeeHelper；记录安装步骤、首次成功时间、每次复用成功率、失效后修复耗时。未测试前不对外宣传领先。
- [ ] **建立状态与恢复闭环。** 展示匹配、已启用、实际运行、等待权限、失败/冲突的区别；提供停止、日志、回滚和导出诊断。把故障变成可理解的状态。
- [ ] **缩短消费路径。** 让接收者先运行已分享的微应用，再按需安装本地创作能力；先验证这条路径在现有架构下的能力范围。
- [ ] **从现有 13 个 demo 提炼可复用模板。** 每个模板具有输入、输出、权限、适用站点、失败条件、验证步骤与一键试用；至少选一个高频真实流程持续跟踪。
- [ ] **补齐微应用的运行结果契约。** 明确成功、部分成功、需接管、失败；只有业务后置条件满足才报告成功。页面点击成功不能替代任务成功。
- [ ] **测量漏斗与成本。** 在清楚告知和用户选择下收集最少必要的聚合事件；优先本地诊断，避免把页面内容、源码或对话默认上传。

### 中期：证明分享和维护能规模化

- [ ] **可持续更新的分享关系。** 区分安装固定版本、跟随作者、fork 独立维护；保留来源、版本差异、回滚与权限变更提示；不要让一次分享演变为作者可静默扩权。
- [ ] **复用格式与适配器工具链。** 提供机器可读 SDK、类型/schema、能力清单、兼容检测与合成测试页面，减少作者依赖聊天猜测 API。
- [ ] **网站变化后的修复助手。** 收集用户主动提交的脱敏失败证据，在隔离测试或预览里生成修复并比较行为；对不可逆业务动作避免无界重试。
- [ ] **团队试点而非先做大市场。** 共享模板库、参数配置与工作空间隔离，优先验证同事能否直接复用。按需要接入身份、同步和组织能力。
- [ ] **兼容性分级发布。** 按 OS × 浏览器 × Agent × 模型/网络逐项标记已验证/实验/不支持，并让安装诊断显示实际能力。按用户采用频率选择下一组合。
- [ ] **协议实验。** 分别验证 WebMCP 与 MCP Apps 的最小用例，记录传输、权限和 UI 隔离差异，决定哪些值得产品化。

### 长期：在已有复用证据上形成生态

- [ ] **建立作者与维护者机制。** 版本所有权、共同维护、弃用/接管、依赖变更、质量报告、问题反馈与可撤回分发；先有稳定作者，再考虑收费市场。
- [ ] **跨宿主可移植。** 为适合的微应用提供浏览器 UI、MCP 工具/UI 等适配构建目标；始终保留能力降级与行为边界。
